## 不应假定后端已经提供的能力

- Agent 注册和 metadata PATCH 是 workspace-key 管理操作。routes/agent.ts:277–331,618–662 没有业务活动版本 CAS；不能让每个会话拿管理 key 自动更新公告。
- metadata 没有公告专属 TTL；routes/agent.ts:49–62 与 openapi.yaml:2584–2627 的 retention 是显式管理动作，不是三天自动退出机制。首版以客户端有效目录过滤满足发现窗口，不物理删历史。
- node/provider 重复连接仲裁（adapters/node/realtime.ts:590–649）不是“设备＋Pi 会话”的通用租约。客户端仍须明确设备传输所有权及本地会话路由。
- 平台 delivery ACK 不等于协作 accepted，更不等于模型执行完成。后端持久私信也不等于持久任务、离线接单或开机恢复。
- 没有确认 SDK 事件对所有 payload 字段的完整透明转发，也不把 best-effort context 更新视为可靠业务消息。

## 据此采用的最小设计

1. 每设备一次供应专属 Agent 身份和 token；同宿主进程多主会话共享设备传输，在 text 信封内以会话 ID 分流。不为每个新会话登记服务端 Agent。
2. 专用发现频道仅存元数据公告与心跳；客户端按来源绑定、代次、activityRevision 和固定 72 小时形成有效目录。旧记录保留不等于继续可发现。
3. 业务走私信；完整版本化 JSON 放 text，保持实时与 REST 解析一致。应用 messageId／taskId／roundId 与平台 ID 各司其职。
4. 本地持久 inbox 和 REST 连续历史游标独立于平台 ACK；周期对账、重连补查不能只看未 ACK deliveries。业务 accepted 在应用记录可靠写入后才发出。
5. 第一版不新增 A2A SDK、A2A 网关或中央守护服务。使用已有 Node 能力或 Relaycast SDK 的具体依赖取舍仍须核验，未在本轮引入。

## 实现前／端点验收门槛

- 明确一次性设备身份、发现频道供应与认证引用方案，单独授权后才创建或分发；不能以文档存在代替凭据授权。
- 用已供应的两个设备身份验证原生 DM／频道完整链路、sender Agent ID 绑定、text 上限、顺序和重复消息。
- 验证自动 ACK 后崩溃仍从已 ACK 消息的 REST 历史补齐、历史可保留时间、分页边界与游标原子性；若部署保留策略不能覆盖所声明窗口，报告缺口，不静默接受不可靠路径。
- 发现频道初次加入／重连时验证历史与实时竞态、旧撤销晚到、分页容量或历史缺失时显式不完整；离线原设备没有撤销也应在客户端三天后过滤。
- 验证同进程多会话与配置快照的共享生命周期、跨进程设备所有权及会话回收后的暂不可达。不同进程共用一个传输身份的分流未经验证，不预先声称支持。
- 上述为 P0a／V11 的依据与待验清单，不是通过记录。新路线的实际协议审阅与实现授权独立于 v0.5 旧路线审阅。
