# 000.TODO.md 编写与使用说明

## 职责

- 记录当前状态、任务树、阻塞、验收状态和证据指针。
- 作为项目或专题级文档治理入口，维护设计依据、实现、验证、发布和回填的闭环状态。
- 反映真实进展与未闭合项，而不是替代设计正文。
- 不是实时任务看板，也不替代 issue、项目管理系统、会话待办、执行日志或测试报告。

## 适用场景

- 创建或重建设计文档骨架时，需要建立统一状态账本。
- 迁移旧文档或旧流程后，需要汇总未迁完项、残留入口和证据缺口。
- 一轮实施、验证或发布完成后，需要批量回写状态与证据。
- 复核是否仍有遗漏、伪完成、阻塞或外部依赖未闭合。

## 推荐结构

- 优先使用 [000.TODO.md 模板](../assets/000-todo.template.md) 作为起始模板。
- 默认结构只有 `## 树形 TODO`。
- `## 树形 TODO`：父节点聚合；普通执行叶子默认只写 `前置依赖 / 验收证据`，只有当前阻塞影响推进或验收时才补 `阻塞`；若项目确实需要筛选或统计，可额外加可选标签，如 `类型`。
- 完整性复核、遗漏回填、更新触发等维护说明保留在 reference，不进入默认模板主体章节。

## 可选视图

- `## 说明`：仅当项目需要在文档内声明本项目编号口径、维护规则或边界说明时添加，保持极简。
- `## 简短总览`：仅当 TODO 树过长、读者需要快速定位当前阶段时添加，不能替代任务树。
- `## 关键路径`：仅当跨工作包依赖链很长时添加；优先使用节点 `前置依赖` 字段，关键路径视图不得成为第二套任务图。

## 必填内容

- 当前状态、任务树、阻塞、验收状态、证据指针。
- 每个工作包的设计依据指针和验收证据入口。
- 真实进度口径，至少覆盖未开始、进行中、阻塞、待验证、已完成。
- TODO 条目的增删改一定涉及文档变更，必须能追溯到文档依据或证据变化。
- `checkbox` 通常在一轮实施完成后结合证据批量标记，不应边执行子任务边同步打勾。
- 若一次性执行未完成，应先回写结果、失败原因或偏离点，再调整对应设计文档和 TODO 条目。
- 若执行中发现 TODO 本身不可执行，应先记录偏离、阻塞证据或失败原因，再调整对应 A/B/C 文档，最后调整 TODO 条目。
- 生成的项目 `000.TODO.md` 默认不受一般文档的 300-500 行建议限制，但项目明确行数规则优先；本技能包内所有文件仍须不超过 500 行。
- TODO 只记录状态与证据指针；风险分析正文应放回对应主文档，而不是作为普通执行叶子的固定字段。

## 编号规范

- 编号表达任务树归属，不表达文档编号；总目标不编号，只在标题或说明区描述。
- 编号由固定七级形态组成，层级不靠推断，直接按格式判定：
  1. 第 1 级：`A-1`
  2. 第 2 级：`A-01`
  3. 第 3 级：`AB-01`
  4. 第 4 级：`ABC-01`
  5. 第 5 级：`ABC-001`
  6. 第 6 级：`ABC-0001`
  7. 第 7 级：`ABC-00001`
- `ABC-00001` 是第 7 级，也是最后一层实际任务；实际任务必须使用第 7 级格式，不使用其他格式作为实际任务，也不允许再向下挂子项。
- 第 1-6 级都是组织层，可按项目复杂度裁剪；新项目推荐从第 3 级 `AB-01` 开始建立，避免后续项目扩张时没有高层编号可用。
- 若后续需要更高层聚合，可以向上补第 1 级 `A-1` 或第 2 级 `A-01`，但不改动既有下层编号归属。
- 子项必须沿固定层级向下走，且子项编码号必须继承父项编码号。
  - 合法：`AB-01 -> ABC-01 -> ABC-00001`。
  - 合法：`ABC-01 -> ABC-001 -> ABC-0001 -> ABC-00001`。
  - 合法：裁剪中间组织层后直接使用 `AB-01 -> ABC-00001`。
  - 非法：`ABC-001 -> ABC-01`，因为子项不能回到更高层格式。
  - 非法：`AB-01 -> XYC-00001`，因为子项前缀没有继承父项编码号。
- 可以裁剪中间组织层，但不能反向回到更高层格式，也不能混用不继承父项编码号的前缀。
- 实际任务的三字母前缀应尽量取所属模块、能力域或工作包的首字母，并在项目内保持唯一。
- 每个工作包或任务组的首个实际任务 `ABC-00001` 固定为 A/B/C 文档依据验收任务，必须指向 `A00`、`B00`、`C00` 系列中的某个文档或其子文档，用于确认后续任务的文档依据已经存在且足以支撑推进；未通过前，不推进该工作包或任务组的后续实现、测试、部署或联调子项。
- `ABC-00001` 的 `证据:` 必须填写 A/B/C 文档路径、章节、评审记录或设计依据指针；如果环境、发布、接口或数据等依据重要，应先沉淀到对应 A/B/C 文档，再由 `ABC-00001` 指向该文档依据。
- 编号一旦发布，不因排序、插入、删除或展示方式变化而重排。
- 删除、废弃或迁移的编号不复用；必须保留废弃说明、迁移说明或证据指针，保证后续可追溯。
- TODO 条目的增删改一定涉及文档变更；编号变化本身也算文档变更，必须同步回写依据或说明。
- `checkbox` 不是实时进度；执行完成后一轮批量回写状态和证据，避免边执行边改编号或边做边打勾。

## 不应写入

- 需求、架构或详细设计的长篇正文。
- 用 TODO 条目替代正式设计决策或详细实现说明。
- 执行子任务时的实时流水账式过程记录。
- 执行过程中的临时进度、试错记录、命令输出或局部 todo；这些内容应留在执行会话、issue/MR、测试报告或其他执行记录中。
- 因为“做了一步”就即时回写 TODO，或边执行边勾 `checkbox`。
- 与文档依据无关的孤立 checklist 或平行状态账本。

## 与其他文档的关系

- 本文件引用 `000.名词解释.md`、`A00.需求分析.md`、`B00.规划设计.md`、`C00.执行计划/详细设计.md` 的结论，不复制其正文。
- 需要判断内容是否应回退到其他主文档时，先读 [设计文档职责边界](design-doc-boundaries.md)。
- 轻量追踪关系建议保持为 `A00` 需求 ID -> `B00` 模块/接口 -> `C00` 文件/函数/测试 -> `000.TODO.md` 状态与证据指针。
- 设计决策变更应先更新对应主文档，再在本文件回写状态、缺口和证据指针。
- 创建或重建时应参考 [000.TODO.md 模板](../assets/000-todo.template.md)，保持字段和复核入口一致。

## 更新触发条件

- TODO 条目发生增删改，即文档依据、任务树结构或治理结构发生变化。
- 一轮实施、验证、部署或联调结束，需要批量勾选 `checkbox` 并补证据指针。
- 一次性执行未完成，需要记录失败原因、偏离点、阻塞证据，或据此调整后续文档和 TODO。
- A/B/C 文档发生变化，需要同步状态、缺口和证据指针。
- 验收结果、证据入口或阻塞状态发生变化，需要更新证据指针。

## 复核要点

- 是否清楚记录当前状态、阻塞、验收状态和证据指针。
- 是否错误承载了设计决策正文。
- 风险分析正文是否被错误写进 TODO，而没有回到对应主文档。
- 是否把临时进度、试错记录、命令输出或局部 todo 误写进 TODO。
- 是否把 TODO 当作实时看板，替代其他执行记录或协作系统。
- 是否出现边执行子任务边同步修改 TODO 的痕迹。
- `checkbox` 是否基于可复核证据批量更新，而非主观估计。
- 工作包首项是否先完成 A/B/C 文档依据验收，再推进实现、测试、部署和联调。
- 编号前缀表、编号稳定性、废弃编号说明和编号映射是否完整。
