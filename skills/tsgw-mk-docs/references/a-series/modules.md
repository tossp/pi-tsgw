# A00.需求分析.md 模块裁剪

## 必选最小模块

- `Why`：背景、问题、触发原因。
- `What Changes`：本次要改变什么能力、行为或边界。
- `Scope / In / Out`：本次覆盖范围与明确不覆盖范围。
- `Requirement` + `Scenario` / 验收场景：每条需求带稳定 ID，至少绑定一个可验证场景。

## 常用可选模块

- `Capabilities`：按能力簇整理需求，而不是平铺罗列。
- `Impact`：对现有流程、角色、上下游或兼容面的影响。
- `Non-Goals`：主动声明不做什么，防止范围漂移。
- 用户 / 场景：按角色、输入面、业务情境组织需求。
- 非功能需求：性能、安全、可靠性、可观测性、兼容性、合规。
- 外部接口需求：对外输入输出、第三方约束、协议前提。

## 中大型项目模块

- SRS 式引言：目的、范围、术语、参考资料、文档约定。
- 总体描述：产品环境、用户类别、运行约束、假设依赖。
- 功能需求：分组需求、优先级、业务规则、异常情形。
- 非功能需求：质量属性、容量、性能、安全、审计、可运维性。
- 外部接口需求：用户接口、软件接口、硬件接口、通信接口。
- 验收标准：按需求 ID 给出验证条件与通过标准。
- 需求追踪矩阵：把需求映射到 `B00` 模块 / 接口和 `C00` 验证入口。

## 组织原则

- 先写最小闭环，再按风险补可选模块。
- 每条需求保持稳定 ID，不因排序调整而改号。
- 每条需求至少要有一个可验证场景；只有描述没有验证入口的条目不算完成。
