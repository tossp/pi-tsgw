# 设计文档职责边界

## 目的

- 用于判断内容应写入 `000.名词解释.md`、`000.TODO.md`、`A00.需求分析.md`、`B00.规划设计.md` 还是 `C00.执行计划/详细设计.md`。
- 用于文档迁移、骨架补齐、完整性复核时统一口径，避免需求、架构、实现、状态和术语相互串层。

## 判断口诀

- 要不要做 / 为什么做 / 完成标准 -> `A00.需求分析.md`
- 系统怎么分 / 模块怎么协作 / 协议边界怎么定 -> `B00.规划设计.md`
- 代码怎么落 / 怎么迁移 / 怎么测 / 怎么发 -> `C00.执行计划/详细设计.md`
- 现在做到哪 / 卡在哪 / 证据在哪 -> `000.TODO.md`
- 术语怎么叫 / 哪些名字禁止 -> `000.名词解释.md`

## 决策表

| 关注点 | 应写入 | 应包含 | 不应包含 |
| --- | --- | --- | --- |
| 术语与命名治理 | `000.名词解释.md` | 术语定义、别名、禁止词、命名冻结、跨文档术语一致性 | 需求正文、架构设计、实现计划 |
| 当前推进与验收状态 | `000.TODO.md` | 当前状态、任务树、阻塞、验收状态、证据指针 | 设计决策正文、长篇方案说明 |
| 需求与成功标准 | `A00.需求分析.md` | 背景、目标、非目标、场景、需求、约束、成功标准、验收口径 | 架构拆分、模块协作、代码落点 |
| 系统设计与边界 | `B00.规划设计.md` | 总体架构、模块职责、接口/协议/数据模型口径、系统级策略、方案取舍 | 代码改动清单、实施状态 |
| 落地实现与发布验证 | `C00.执行计划/详细设计.md` | 代码落点、目录/包/模块映射、实现细节、配置/脚本/命令、迁移/发布/回滚、验证入口 | 新增需求、推翻 B 层架构 |

## `000.名词解释.md`

### 负责内容

- 统一术语定义，明确一个概念在全文档体系中的唯一主叫法。
- 记录别名、历史名称、易混淆说法、禁止词。
- 说明命名冻结规则，避免后续文档在同一概念上反复改名。
- 维护跨文档术语一致性，作为 A/B/C/TODO 的命名基线。

### 不负责内容

- 不承载需求背景、目标、约束或验收口径。
- 不承载架构分层、模块协作、协议设计。
- 不承载实现计划、迁移步骤、测试命令。

## `000.TODO.md`

### 负责内容

- 记录当前状态、任务树、阻塞、验收状态。
- 维护证据指针，例如指向设计章节、实现变更、测试结果、联调记录、发布验证入口。
- 作为持续更新的状态账本，反映真实推进情况与未闭合项。

### 不负责内容

- 不承载设计决策正文。
- 不复制 A/B/C 中的大段论证、架构说明或实现细节。
- 不承载风险分析正文；风险判断应落在 A/B/C 对应层级，TODO 只记录阻塞、状态和证据。
- 不用 TODO 代替正式需求文档、架构文档或详细设计文档。

## 扩展文档归位表

| 内容 | 默认归位 |
| --- | --- |
| ADR | 默认归 `B` 系列 `Decisions`；决策很多时可拆成 `B` 系列子文档。 |
| API | 高层契约、边界、兼容策略归 `B`；字段、schema、命令、兼容测试细节归 `C`。 |
| 测试计划 | 归 `C`；`A` 只写验收口径，`B` 只写质量策略。 |
| 发布 / 回滚 | 归 `C`；`B` 可写部署视图或发布策略，TODO 只写状态和证据指针。 |
| 安全 | 安全需求归 `A`；威胁模型、控制策略归 `B`；验证、加固步骤和测试入口归 `C`。 |
| 运维 / Runbook | 常规操作步骤归 `C` 或外部运维文档指针；TODO 只记录状态和证据。 |
| 用户文档 / README / 贡献指南 | 不属于 A/B/C 强制骨架；可作为外部文档或项目文档入口，不纳入默认顶层。 |

## Micro Mode / 小项目最小模式

- 小项目或低风险改动可只维护最小 `A00` + `C00` + `000.TODO.md`。
- `000.名词解释.md` 是否单独创建，按术语复杂度决定。
- `B` 系列仅在系统边界、架构、协议、数据模型、安全或性能策略发生变化，或现有口径存在歧义时单独产出。
- 即使采用 micro mode，仍要保留 `A` 的完成标准、`C` 的验证入口、TODO 的证据指针。

## `A00.需求分析.md`

### 负责内容

- 回答为什么做、要做什么、做到什么算完成。
- 记录背景、目标、非目标、用户或业务场景、需求清单、约束、成功标准、验收口径。
- 定义问题空间和结果边界，为 B/C 提供稳定输入。

### 不负责内容

- 不写系统架构拆分、模块职责划分。
- 不写接口协议、数据流细节、代码目录或包路径。
- 不写实现进度、任务状态或回滚步骤。

## `B00.规划设计.md`

### 负责内容

- 回答系统怎么分、模块怎么协作、协议/边界/数据流怎么定。
- 记录总体架构、模块职责、接口与协议约定、数据模型口径、系统级策略、方案取舍。
- 说明关键设计决策及其理由，为 C 层实现提供边界条件。

### 不负责内容

- 不写代码改动清单、文件逐项修改计划。
- 不写当前实施状态、任务完成度、验证进展。
- 不把临时实现细节上升为架构原则。

## `C00.执行计划/详细设计.md`

### 负责内容

- 回答代码怎么落、怎么迁移、怎么测、怎么发。
- 记录代码落点、目录/包/模块映射、实现细节、配置/脚本/命令、迁移/发布/回滚、验证入口。
- 把 B 层设计转换成可执行的实现与验证路径。

### 不负责内容

- 不新增需求，不修改完成标准。
- 不推翻 B 层已确定的总体架构和模块边界；若确需调整，应先回到 B 层补决策。
- 不用实现便利性倒逼需求改写。

## 回退规则

- 如果 `000.TODO.md` 的设计依据验收失败，先判断缺口属于哪一层：
  - 术语不清、命名冲突 -> 补 `000.名词解释.md`
  - 为什么做、做什么、完成标准不清 -> 补 `A00.需求分析.md`
  - 模块边界、协议、数据流或方案取舍不清 -> 补 `B00.规划设计.md`
  - 代码落点、迁移路径、验证入口或发布回滚不清 -> 补 `C00.执行计划/详细设计.md`
- 对应文档补齐后，再回写 `000.TODO.md` 的状态、阻塞变化和证据指针。
- 不在 TODO 中临时塞入设计正文来“补齐”依据。

## 常见误放

- 把“为什么需要这个能力、什么情况下算完成”写进 `B00`：应回到 `A00`。
- 把“服务拆成几个模块、边界如何约束”写进 `C00`：应回到 `B00`。
- 把“修改哪些目录、执行哪些命令、如何回滚”写进 `A00`：应移到 `C00`。
- 把“当前卡在外部依赖、测试结果在哪里”写进 `B00` 正文：应记录到 `000.TODO.md` 并附证据指针。
- 把“同一个概念出现多个叫法，哪些用词禁止”散落在 A/B/C 中：应统一收敛到 `000.名词解释.md`。

## 迁移与复核提示

- 迁移混合文档时，先按术语、需求、设计、执行、状态五类拆分，再决定落点。
- 确定拆分方案后、执行任何文件写入前，逐一列出将从哪个文件的哪个段落或章节搬移到哪个目标文件，完整展示全部迁移计划。
- 等待用户明确授权后，才执行实际搬迁；涉及删除或改写原文件内容的操作，与新增同等对待，一并纳入确认范围。
- 复核文档完整性时，先看 `A00` 是否定义完成标准，再看 `B00` 是否给出系统边界，再看 `C00` 是否提供落地与验证路径，最后看 `000.TODO.md` 是否反映真实状态和证据。
- 当多个文档都涉及同一事实时，以层级职责判断主归属，其余文档只保留引用或摘要，不重复承载整段正文。

## 轻量追踪关系

- 推荐用最小链路串起四层：`A00` 需求 ID -> `B00` 模块 / 接口 -> `C00` 文件 / 函数 / 测试 -> `000.TODO.md` 状态与证据指针。
- `000.TODO.md` 只保留状态和证据指针，不复制追踪矩阵正文。
