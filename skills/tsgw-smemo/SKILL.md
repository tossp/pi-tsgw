# 记忆系统 (smemo)

本技能在各设备的 PiWeb／OC 中使用同一正文和参考资料，统一职责与维护权限；宿主差异仅限工具接入。跨设备共享的是 Blinko 知识，技能和规则文件仍需在各设备的本地维护来源同步更新。

## 定位与职责边界

- **记忆系统**：通过 Blinko 跨设备、跨会话、跨项目共享外部知识、通用资料、经核验有效的资讯及可复用解决方案。
- **smemo**：这套职责与维护流程的技能名；不是另一份数据库。
- **系统记忆**：Magic Context 的 `ctx_memory` 及相关工作延续机制，PiWeb／OC 在同一设备的共享数据库下互通；项目、会话仍有作用范围，各设备数据库不共享，不能用它冒充 Blinko 已写入。
- 插件注入的记忆规则治理整套体系；项目多层级 `AGENTS.md` 维护项目指引、长期专有规则与方法，详细设计及现场资料按项目既有分类归位。

### 不进入 Blinko 的内容

- **个人倾向性信息**：个人偏好、沟通风格、行为画像及其推断。由 Magic Context 原生全局用户记忆／`<user-profile>` 机制依实际配置处理；用户明确要求持续执行的规范写入用户级规则，不通过 smemo 维护画像。
- **具体现场事实**：设备身份、地址、运行状态、实际部署、配置、版本、权限、入口映射及一次性排障观察，即使稳定、需要跨设备查询或属于调研证据，也不写入 Blinko。正式事实归所属项目资料，需要工作接续时可留本机 ctx 摘要，不能只搬到某台 ctx 就称已共享。
- 无法脱离项目成立的内部需求、设计、决策与实现约定，及必须即时执行的编排、授权、提示词行为规则。规则落适用 `AGENTS.md`／代理提示词，详细内容落项目权威资料。
- 当前执行步骤、临时状态、未定项目方案和明显无后续价值的输出。当前步骤用 `todowrite`，延期意图及发现用 `ctx_note`，讨论与原始证据留历史。
- 密钥、凭据、受保护内容及不应进入共享知识库的敏感材料。

上述排除项不因一句“记住”而改变落点。已有现场记录按单独安排的迁移范围处理，不因技能更新顺手盘点、迁移或清空旧库。

## 主动触发与沉淀标准 (MUST)

在当前任务或相关知识维护中发现以下内容，应主动检索、写入或更新，不必等待用户逐条提醒：

- 外部调研形成的通用／外部知识（必须沉淀，不以项目已采用为条件）；
- 可跨设备复用的通用知识、流程、解决方案、最佳实践及适用边界；
- 外部／通用知识范围内的稳定事实和经核验仍有效的资讯；
- 从反复问题、失败经验或纠正中提炼出的可复用知识，不复制具体现场过程；
- 用户明确要求保留、且符合职责边界的其他非敏感长期信息；该类信息不是默认主动采集类别。

这是开放清单，不要求苛刻证明未来一定复用。时效短不等于没有价值：有效资讯或历史外部结论可保留核验时间和适用边界，但不能用这一点绕过个人倾向、现场事实或敏感信息的排除规则。

## 检索与记录质量

### 冲突处理

- 普通记忆的旧笔记与新事实冲突时 → 更新原笔记并记录变更原因
- 外部知识的范围、冲突和历史结论按“外部知识沉淀”处理；不要把相近主题误作重复笔记
- 优先保持信息的完整性而不是堆砌数量

### 重复记忆处理 (MUST)

- 使用记忆系统时发现同一范围的重复或相似笔记 → 搜索并确认现有主记录，优先更新它
- 对其他重复笔记，先提取仍有价值的差异内容，合并写入主记录
- 可自主修正标签、更新或合并记录、归档或删除无价值重复记录及恢复误归档记录；方向或范围不同的外部知识应独立且互相关联，不得错误合并。

### 标签

从笔记内容提取多个关键词，形成多维度关联；标签用词保持一致（如统一使用 `#Linux`，不混用 `#linux`）。按实际内容自然使用普通标签或层级标签，例如 `#python`、`#技巧/linux`、`#运维/晨云`，不预设复杂体系。命中且复用时校验标签，补齐内容关键词并修正不一致用词。

### 查询策略 (MUST)

- **先分流，再按需请求 Blinko**：提到“记忆”时先判断职责；项目现场、个人倾向或当前任务不因此触发外部搜索。需要查询或维护共享知识时检索 Blinko，本轮已查且仍可用的结果可复用。非明确外部调研，且当前上下文或 ctx 已足够、本次无需查询或维护 Blinko 时，可不请求 Blinko；明确外部调研仍须历史查询、当前核验与自动沉淀。
- **先用关键词，再用标签组合**：关键词宽搜 -> 标签精确
- 需要外部知识时，先查项目资料和相关记忆，将命中内容作为历史基线：复用来源和关键词，识别分歧、边界与证据缺口，提高本轮调研的准确性和广度。
- 对明确的外部调研任务，命中记录不得自动停止外部调研；按本次问题开展当前外部补充或事实核验。已有记忆可决定检索范围和强度，但不能替代事实核验；核验强度应与知识的风险和时效相关，无须每次无差别从零开始。
- 命中条目时检查其来源、适用边界、状态和时效信息，并为后续比较保留稳定条目 ID 或链接。

### 维护、清理与验证 (MUST)

- **持续维护授权包含删除**：与当前任务或知识维护直接相关的创建、单条或批量更新、标签调整、合并、归档、恢复及删除（含永久删除），模型可自主判断执行，无须逐条确认；不强制先标记 `#待删除`、归档或备份。
- 写入前检查同范围主记录，优先更新；重复记录先合并独有价值并验证主记录，再按价值决定保留、归档或删除。方向或范围不同的知识不要错误合并。
- 外部知识失效、被替代或存在冲突时，根据证据和历史价值更新、关联、归档或删除；需要追溯的结论可用 `#已过期`、`#已替代`、`#待复核`、`#待确认` 等状态，不能只因陈旧就判断无价值。
- 不确定内容保留未决依据，先核验，不伪造一致结论。已有现场条目的迁移按所属项目和当次确认范围执行，保留有价值通用部分与必要引用，不借维护授权展开无关全库清理。
- 先读取实际目标及工具定义，再做相关增量；验证返回结果和更新后正文／状态。删除须按实际入口区分回收站与永久删除，不能把普通列表无命中当作已永久删除的证据，也不承诺永久删除可恢复。
- 每次创建、更新、合并、归档、恢复或删除后，回报实际动作、条目 ID、简短变化／理由及替代条目 ID（如有）。不输出敏感内容，不把未执行动作当作完成。
- 普通更新利用已具备的版本历史追溯；不为自由删除承诺不存在的恢复能力。维护授权不扩展到文件、Git、服务、凭据、访问权限或定时任务。

## 外部知识沉淀 (MUST)

1. **建立历史基线**：先搜索相关记忆，复用既有来源和关键词，识别与本次问题的分歧、范围和证据缺口；命中不是跳过调研的条件。
2. **进行本轮核验**：对明确的外部调研任务，始终按本次问题做当前外部补充或验证。比较本次问题范围、技术/产品/规范版本、来源发布日期或内容版本、证据检索/事实核验时间，以及适用环境和最佳实践变化。
3. **按比较结果维护**：
   - 同一范围且仍有效：补充最新证据，记录本次核验信息。
   - 同一范围但事实或最佳实践变化：更新当前结论，明确旧结论的历史适用范围、被替代时间和原因，并标记 `#已替代`（或适用的状态）。
   - 相近主题但方向或范围不同：建立独立且互相关联的条目；不得粗暴覆盖或错误去重。每个主题保留明确的当前结论入口。
   - 新旧证据冲突且无法裁决：保留冲突和各自证据，标记 `#待确认`（或等价状态），不得伪造统一结论。
4. **调研后 upsert**：检查同范围主记录，已在本轮确认且仍适用的检索结果可复用；仅同一范围时优先更新主条目，不存在时新建。外部调研形成的外部知识必须写入，不因尚未被项目采用或未证明可复用而跳过。
5. **项目侧引用**：项目 docs 只记录项目的采用或否决判断、取舍理由和应用方式，并引用对应记忆条目及必要的采用时版本或核验时间，不复制完整调研正文。

### 外部知识条目正文格式

每个条目保持简洁、可检索和可维护，至少包含标题、标签及以下字段：

```markdown
#领域 #主题 [#状态]

## 标题

- 调研问题/范围：...
- 来源链接或对象标识：...
- 来源版本/发布日期或内容版本：...（与时效相关时）
- 关键证据或定位：...（链接、章节、段落、版本或可复核摘录）
- 证据检索/事实核验时间：...（与时效相关时）
- 结论：...
- 适用版本/环境、边界或限制：...
- 历史关系/替代说明：...（相关条目、旧适用范围、被替代时间与原因；适用时）
```

- 视需要加入状态；与时效有关时必须记录来源版本/发布日期、证据检索或事实核验时间、适用版本或环境。
- Blinko 自动维护的创建/更新时间仅是条目操作元数据，不等于来源时间、最后事实核验时间或结论有效期；不要在正文机械重复，也不得将“最后修改时间”当作知识仍有效的证据。
- 当前权威结论必须有明确入口；历史结论不得伪装为当前最佳实践，但应保留可追溯的旧适用范围和替代原因。

- 适用环境记录可复现的软件／规范条件，不记录具体受管设备的身份、当前版本、IP、端口、部署路径或权限。现场证据和项目采用记录归所属项目资料，不随调研正文进入 Blinko。

## MCP 接入与工具选择

只规定工具职责，不固定跨宿主调用前缀或参数模板。以下 `blinko__*` 是服务端工具名，实际名称、参数类型和能力以当前会话定义为准。

### 宿主适配

- **Pi／Pi Web**：使用 Pi 原生 MCP。工具未直接暴露且本会话提供 `codemode` 时，用 `searchTools()`／`describeTool()` 发现并读取定义，再按实时 schema 调用。原生注册名通常为 `mcp__ts_tool__blinko__*`，仍以发现结果为准；`/mcp` 用于连接管理，不是工具调用网关。
- **OpenCode**：使用当前 OC 会话提供的工具清单或已提供的发现入口，不套用 Pi 专属 codemode／MCP 前缀，也不沿用旧适配器格式。
- 工具未提供、连接或认证失败时说明限制；不猜测调用名、不寻找或回显凭据、不放宽访问控制，不用其他记忆入口冒充 Blinko 写入成功。

| 服务端工具 | 用途 |
| --- | --- |
| `blinko__searchBlinko` | 关键词宽搜，再按标签与实际过滤能力检索 |
| `blinko__upsertBlinko` | 无同范围主记录时创建 |
| `blinko__updateBlinko` | 修正、补充、维护状态或合并到主记录 |
| `blinko__deleteBlinko` | 按持续维护授权删除无保留价值的条目 |
| `blinko__createComment` | 当前任务确有需要时评论 |
| `blinko__createScheduledTask`／`blinko__listScheduledTasks`／`blinko__deleteScheduledTask` | 定时任务的对应操作；不从条目维护授权推定可创建、修改或删除定时任务 |

定时任务只有用户明确表达相应意图时才处理。不要从技能或历史 API 摘录复制参数；数组、对象、布尔值和数字须按实时 schema 使用原生类型。

## 分流与维护示例

```text
外部调研或通用知识 → 按 MUST 规则检索、核验并沉淀 Blinko。
项目现场／个人倾向／敏感内容 → 分别归项目资料／user-profile／受保护位置，不写入 Blinko。
发现重复条目 → 合并独有价值、验证主记录，再按授权决定归档或删除并回报。
用户明确要求定时任务 → 核对范围后处理；不从普通条目维护授权推定可操作定时任务。
```
