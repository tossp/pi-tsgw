# Go 代码审查：中文阅读入口与要点

本文根据本轮完整读取的本地已有资料自主组织，仅供离线审查和定位问题。不是官方全文、逐字译本、完整规范或本轮核验的最新版。

官方阅读入口：<https://go.dev/wiki/CodeReviewComments>。它是常见审查问题的补充清单，不替代 Effective Go 或项目明确的协议要求。

JSON PascalCase、omitzero 优先和随真实功能或修复迁移旧标签，是 [本技能强制约定](../SKILL.md)，不应冒称为官方审查文档的统一要求。

## 格式、名称和文档

- 使用 `gofmt`；导入分组，标准库在前。除避免名称冲突外，不随意重命名导入。
- 多词名称用 MixedCaps 或 mixedCaps；缩写形式保持一致，例如 `ServeHTTP`、`appID`。
- 包名要简短且有意义，避免 `util`、`common` 等模糊名称；导出名称不重复包名。
- 局部短作用域可用短变量名，距离声明越远越需要描述性名称。接收者名保持简短一致，不用 `this`、`self`。
- 导出声明有文档注释，以声明名称开头并写完整句子；复杂的未导出声明也应解释用途。
- 包注释紧邻 package 声明。新增包提供使用示例或展示完整调用过程的测试。
- 按语义和可读性断行，不为固定行长机械拆分。

## 错误与控制流

- 检查所有返回的错误，处理或返回，不用 `_` 静默丢弃，不用 `panic` 处理普通失败。
- 用独立的 `error` 或 `ok` 返回值表达失败，不占用正常结果的特殊值。
- 错误分支尽早返回，使正常路径保持较少缩进。
- 错误字符串通常小写开头、末尾不加标点；专名或缩写遵循其本身写法。
- 命名返回值应消除歧义而不是重复类型说明；较长函数显式列出返回值。

## 接口、值与接收者

- 按实际需求在使用方定义精简接口；实现方通常返回具体类型。不为假想需求或仅为 mock 提前创建接口。
- 不为节省几个字节机械传指针，尤其不要随意传接口的指针。
- 复制值前考虑别名和内部状态；含互斥锁等同步字段的结构不能随意复制。
- 修改接收者状态时用指针接收者；大结构的复制成本也应考虑。接收者形式保持一致，不机械给 map、func、channel 再套指针。
- 空 slice 声明通常可用 nil slice；涉及 JSON 等可观察输出时，不能无视项目对 nil 与非 nil 空值的区别。

## 上下文和并发

- 需要上下文的函数通常把 `ctx context.Context` 放在首个参数，而不是存入结构体；沿调用链传递取消、期限等信息，不自造替代类型。
- 优先同步函数，把额外并发的选择留给调用者。
- 创建 goroutine 时明确退出路径，检查 channel 收发是否可能永久阻塞，防止泄漏和数据竞争。

## 安全、导入与测试

- 密钥等安全随机需求使用 `crypto/rand`，不要使用 `math/rand`；本页不新增具体版本 API 的可用性断言。
- 仅为副作用导入的包应限制在主程序或确有需要的测试中；避免点导入，不能为方便污染普通代码的命名空间。
- 测试失败信息应说明操作、输入、实际结果和期望结果，而不是只输出“失败”。
- JSON 改动另外检查实际键名、零值与空值、自定义 `IsZero() bool`、真实变更触及的旧标签及公共协议边界；冲突先暴露并确认，不把审查建议作为破坏协议的授权。
