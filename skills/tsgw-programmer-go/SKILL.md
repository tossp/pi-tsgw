# Go 编程技能（Pi 版）

编写简洁、地道、可维护的 Go 代码。适用于新增代码、审查、重构、调试和 Go 相关问答。Pi 可按任务加载，也可用 `/skill:tsgw-programmer-go` 显式调用。

## 规则来源与执行边界

- 下述 JSON 命名、省略策略与迁移规则是用户认定的最佳实践，属于**本技能约定**，必须执行；不是可选建议，也不冒称来自 Effective Go。
- Go 惯用法的阅读入口是 [Effective Go](https://go.dev/doc/effective_go) 和 [Code Review Comments](https://go.dev/wiki/CodeReviewComments)。本地 references 是自主组织的中文要点，不是官方全文，不代表本轮核验的最新版；Effective Go 也不能覆盖所有现代 Go 主题。
- 先检查项目明确的协议、兼容性要求和 Go 工具链约束。若与本技能约定冲突，必须指出具体字段、消费者及可能破坏的行为，向用户确认迁移范围和兼容方案；确认前不得擅自破坏公共协议。不得以“兼容”为由悄悄删除或降级本技能约定。
- 本技能不引入依赖，不依赖 OpenCode 专属工具。离线任务仅阅读本地资料；不能验证的版本能力应报告不确定性，不新增未经核验的新版本知识。

## Go 基础约定

- **格式化**：始终使用 `gofmt`，没有例外。
- **命名**：多词名称不用下划线；导出名称用 MixedCaps，未导出名称用 mixedCaps。包名简短、小写；缩写保持一致，例如 `ServeHTTP`、`appID`。
- **错误处理**：始终检查错误，处理或返回错误；不用 `panic` 处理普通错误，不用 `_` 悄悄丢弃错误。正常路径少缩进，错误分支尽早返回。
- **并发**：通过通信共享内存，使用 channel 表达协作；明确每个 goroutine 的退出条件，避免阻塞与泄漏。优先同步接口，让调用者决定是否并发。
- **接口**：保持精简，理想情况下 1–3 个方法；接收接口，返回具体类型。根据实际使用需求定义接口，不为假想需求预建接口。
- **文档**：为所有导出符号编写文档，以符号名称开头；复杂的未导出声明也应说明用途。

## JSON 强制约定（本技能）

### 零值省略

在 `encoding/json` 中，若要根据**零值**省略字段，包括自定义 `IsZero() bool` 逻辑，优先使用 `omitzero`，而不是 `omitempty`。**仅当明确需要“空值”语义而非“零值”语义时，才使用 `omitempty`**。不能不区分语义就机械替换；若项目工具链不能满足所需能力，暴露约束并确认处理方案，不擅自升级工具链或静默改用不同语义。

### 命名与标签

- 全局保持一致，默认使用 **PascalCase**。
- 唯一命名例外是**解析（消费或解码）来自不可控外部来源的 JSON**，例如第三方 API 响应、ADB 协议或上游工具输出；此时使用 `snake_case` 或该来源的原始格式。该例外不自动扩展到我们自己生成的输出。
- 对于 JSON 表示由**我们自己生成**的任何 struct，包括 API 响应、CLI 输出、文件格式或配置清单，始终使用 PascalCase。若既有明确协议与此冲突，按前述边界暴露并确认，不能直接破坏协议。
- Go 字段名已能生成所需 PascalCase JSON 键时，优先不指定重命名。
- 仅需省略零值时用 `json:",omitzero"`。
- 仍需显式指定 PascalCase 名称时用 `json:"FieldName,omitzero"`（此例同时需要零值省略；标签选项仍须服从实际省略语义）。
- 字段既不需要重命名也不需要省略时，不添加标签。
- 同一个 struct 内不得混用多种命名风格。若同一类型同时消费外部格式并生成我们自己的格式，先暴露用途冲突并确认边界，不将外部解析例外当作输出豁免。

### 旧 JSON 标签随真实变更迁移

- 现有代码可能包含早于本约定的 `snake_case` 或 `camelCase` 标签；**新增代码必须始终遵循 PascalCase 规则**，外部解析例外仍按上述限定执行。
- 修改包含旧标签的文件时，在同一次变更中顺带修正相关标签；迁移单位是该次因**真实功能或修复**而被修改的所属 struct，不借机全文件、全仓扫描改写无关 struct。
- 某个旧标签所属的 struct 下次因真实功能或修复被修改时，必须同步修正相关旧标签；不得在同一 struct 中同时保留旧式标签和新增 PascalCase 标签。
- **不要创建仅为统一 JSON 标签的独立迁移 PR**。应自然、渐进迁移，避免不成比例的代码扰动、合并冲突和下游破坏。
- 迁移若触及明确的公共协议或兼容性边界，必须先说明冲突并取得确认；等待确认不是取消迁移规则，不能偷偷改名，也不能默默跳过迁移而声称已合规。

## 执行与检查

1. 阅读目标代码、项目约束和相关测试，判断 JSON 是外部输入还是我们生成的输出，识别本次真实变更触及的 struct。
2. 按需读取 [Go 惯用法要点](references/effective_go.md) 与 [代码审查要点](references/code_review_comments.md)。不要把阅读入口当作完整规范或已验证的最新文档。
3. 完成功能或修复，并按上述规则同步迁移相关标签；有冲突先确认，禁止无关标签大扫除。
4. 对变更的 Go 文件运行 `gofmt`，在项目允许范围内运行相关测试；JSON 改动检查实际键名、零值/空值及自定义 `IsZero` 的省略行为和兼容边界。报告未执行的验证及原因。
5. 汇报功能改动、同步迁移的标签、协议冲突及确认结果，不把尚待确认的事项写成已完成。
